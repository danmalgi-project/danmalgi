# wf-work — 3단계 실행 절차

`worker` 에이전트의 실행 지침. 목표: 계획을 동작하는 코드로 옮기고, 각 단위에서 빌드·테스트를 녹색으로 유지.

## 절차 (작업 단위마다 반복)

1. **입력 확인** — `.claude/workflow/<slug>/02_plan.md`를 읽고 작업을 순서대로 집는다.
2. **TDD** — 실패하는 테스트 작성 → 통과시키는 최소 구현 → 리팩터. 변경한 동작에는 반드시 테스트를 남긴다.
3. **fx 배선 확인** — 새 provider/서비스는 해당 패키지 `module.go`에 등록한다. 배선 누락은 컴파일은 되지만 런타임 fx 조립 실패로 이어지므로 구현 직후 확인한다.
4. **proto 변경 시** — submodule 반영 → `/proto-build` → `pkg/gen` 변경 확인 → handler/mapper/usecase 갱신.
5. **검증** — 단위 종료 시 아래 명령을 실행해 녹색 확인.
6. **기록** — `03_work.md`에 변경/결과/이탈을 누적 기록.

## 실행 명령

```sh
go build ./...      # 빌드
go test ./...       # 테스트
go vet ./...        # 정적 점검
```

## 산출물 형식 (`03_work.md`)

```markdown
# 3단계: 작업 로그 — <제목>

## 변경 요약        (작업별 무엇을·어떻게, 파일 경로 포함)
## 테스트 결과      (실행 명령 + 통과/실패)
## 계획 이탈        (계획과 달라진 점과 이유; 없으면 "없음")
## 미해결/후속      (리뷰가 볼 지점)
```

## 원칙

- 계획을 벗어나지 않는다. 개선이 필요하면 임의로 하지 말고 `## 계획 이탈`에 제안으로 기록.
- 테스트 실패는 추측으로 고치지 않는다 — 근본 원인을 찾거나 에스컬레이션.
- **검증의 최종 근거는 실제 `go build`/`go test` 출력이다.** IDE 진단(gopls)이 이와 어긋나면(TDD로 심볼을 나중에 추가할 때의 stale `undefined: <함수>`, **파일 개명·이동 직후 존재하지 않는 경로 기준 오류나 "미사용 함수" 오탐**이 흔하다) IDE가 아니라 실제 빌드 결과를 신뢰한다. `-race` 검증은 **Windows에서만** PowerShell 툴로 실행하고(Bash sandbox의 cgo 제약 — CLAUDE.md 참고), Linux/macOS에서는 Bash로 그대로 실행한다.
- **테스트 하네스는 프로덕션 진입점을 경유한다.** 하네스가 프로덕션의 배선(handler→usecase→event 같은 연결 코드)을 편의상 재구현하면 **그 배선은 지워도 테스트가 녹색**이라 회귀 감지에서 빠진다 — 가장 검증이 필요한 지점이 가장 검증되지 않는 역전이 일어난다. 경유가 구조상 어려우면(구체 타입 의존으로 fake 주입 불가 등) 재구현한 지점과 "이 배선은 미검증"을 `## 미해결/후속`에 명시한다.
- **포맷 확인은 LF 정규화 사본에 `gofmt -l`로 한다** (절차는 CLAUDE.md Windows 항목). CRLF 체크아웃 때문에 `gofmt -l ./...`은 무관 파일까지 flag하고 CRLF 파일의 `gofmt -d`는 파일 전체를 재작성 형태로 보여줘 실제 위반을 가린다 — **노이즈가 섞였다는 이유로 flag를 통째로 기각하지 말고** 노이즈를 제거한 뒤 변경한 파일만 판정한다. 저장소 전반 재포맷은 금지.
- 스타일은 주변 코드에 맞춘다 (명명·`pkg/errors` 에러 처리·로깅 패턴).
- 리뷰 재작업으로 재호출되면 **지적 항목만** 수정하고 재검증한다.
