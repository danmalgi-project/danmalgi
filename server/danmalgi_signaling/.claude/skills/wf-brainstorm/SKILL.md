# wf-brainstorm — 1단계 실행 절차

`brainstormer` 에이전트의 실행 지침. 목표: 흐릿한 요청 → 계획으로 넘길 수 있는 명확한 문제 정의.

## 절차

1. **사이클 슬러그 결정** — 요청을 대표하는 kebab-case 이름 (예: `dm-read-receipt`). 산출물은 `.claude/workflow/<slug>/`에 모은다.
2. **의도 발굴** — 요청받은 것과 필요한 것을 구분한다. 모호하면 확인 질문을 먼저 던진다 (인라인 실행 시 `AskUserQuestion`, 서브에이전트 실행 시 `## 미해결 질문`에 적재).
3. **코드베이스 탐색** — 관련 계층·모듈·proto를 실제로 읽는다. 시작점 힌트:
   - 진입/계약: `internal/handler/`, `proto/public/`, `proto/private/`
   - 로직/세션: `internal/usecase/`, `internal/manager/`, `internal/signaling/`
   - 배선: 각 패키지 `module.go` (fx)
4. **접근 옵션 도출** — 2~3개, 각각 장단점·리스크·파급 계층. proto/fx 변경을 동반하는지 초기에 표시한다.
5. **정리 & 출력** — 아래 형식으로 `01_brainstorm.md` 작성.

## 산출물 형식 (`01_brainstorm.md`)

```markdown
# 1단계: 브레인스토밍 — <제목>

## 문제 정의
## 현재 상태        (관련 코드/모듈/proto + 제약, 파일 경로 인용)
## 접근 옵션        (2~3개, 각 장단점·리스크·파급 계층)
## 미해결 질문      (계획 전 확정 필요한 결정)
## 권장 방향        (근거 포함, 단 확정 아님)
```

## 원칙

- 이 단계에서는 **코드를 수정하지 않는다** — 탐색과 정리만.
- 추측보다 파일 확인. "없음"도 정보이므로 명시한다.
- **새 계약 표면의 "첫 사례"를 추가하는 요청이면, 그 표면 종류의 인터셉터/미들웨어 체인이 실제로 활성인지 확인한다.** 스트림 rpc만 있던 서버에 첫 unary rpc를 붙이는 식의 **표면 종류 전환**에서는, 쓰이지 않던 체인이 주석·미등록 상태로 방치돼 있어도 아무 증상이 없다 — 그대로 표면을 추가하면 인증·로깅·panic recovery가 전부 없는 엔드포인트가 열리고, 미들웨어가 `ctx`에 심는 값(예: UID)을 읽는 코드는 nil로 터진다. `internal/server/grpc.go`의 unary/stream 체인이 **대칭인지** 대조하고, 비대칭이면 `## 현재 상태`에 경고로 올려 계획의 **선행 작업**이 되게 한다.
- 결정을 강요하지 말고 옵션으로 제시한다.
